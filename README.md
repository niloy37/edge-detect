# edge-detect

[![repo](https://img.shields.io/badge/source-github-181717?logo=github)](https://github.com/niloy37/edge-detect)

**A custom-trained YOLO detector, quantized to INT8, running in real time inside your browser tab.**

🔗 **Live demo: _(deploy pending — see [Deploying](#deploying))_**

No inference server. No frames leave your machine. The model executes on your device through
ONNX Runtime Web — WebGPU where the browser supports it, multi-threaded WASM everywhere else — and
the page reports what it costs, per stage, per frame.

---

## Why this exists

Most "YOLO demo" projects stop at a notebook screenshot. The engineering that matters for edge
deployment happens after training: exporting a graph that a target runtime can actually accelerate,
quantizing it without silently destroying it, keeping pre/post-processing identical across two
languages, and measuring honestly on the hardware you claim.

This repository is that second half, end to end, with the failures left in.

## What's here

| | |
|---|---|
| `ml/` | Dataset config → fine-tune → ONNX export → INT8 PTQ → mAP eval → multi-provider benchmark |
| `web/` | Next.js demo: worker-based inference, live latency HUD, benchmark and write-up pages |
| `web/api/detect.py` | Vercel Python function running the same weights on CPU, for the on-device comparison |
| `web/app/selftest` | Regression check: runs the pipeline on main thread *and* in the worker, asserts they agree |

## Results

Measured, not estimated. Every number on the site is generated by a script in `ml/` and written to
a manifest the pages read — see [Reproducing](#reproducing).

**Quantization** (YOLO11n, COCO-80, 128-image COCO subset — see [Known limits](#known-limits-and-what-id-do-next)):

| | FP32 | INT8 | |
|---|---|---|---|
| Model size | 11.10 MB | 3.65 MB | **3.04× smaller** |
| mAP50-95 | 0.5074 | 0.4094 | **−0.098** |
| mAP50 | 0.6738 | 0.5565 | −0.117 |

Calibration method matters more than it gets credit for. Same weights, same 96 calibration images:

| activation calibration | mAP50-95 |
|---|---|
| MinMax (ORT default) | 0.3980 |
| Entropy | 0.3980 |
| **Percentile (99.999)** | **0.4094** |

**Latency**, RTX 5070 / Ryzen 9 5900X, batch 1, 50 warm-up discarded, 300 timed iterations:

| precision | provider | 320px | 640px |
|---|---|---|---|
| FP32 | CPU | 11.45 ms | 37.95 ms |
| FP32 | CUDA | 13.10 ms | 13.88 ms |
| FP32 | **TensorRT** | **4.27 ms** (234 fps) | **5.29 ms** (189 fps) |
| FP32 | TensorRT, static shapes | — | **3.15 ms** (318 fps) |
| INT8 | CPU | 10.74 ms | 34.31 ms |
| INT8 | CUDA | 31.75 ms | 31.04 ms |
| INT8 | TensorRT | failed | failed |

**In-browser** (Chrome, ONNX Runtime Web, 640×640, INT8): ~195 ms single-threaded on the main
thread, ~95 ms in a worker with 4 threads. The live demo, single-threaded end to end: preprocess
6.9 ms, inference 203.5 ms, decode + NMS 1.8 ms, total p50 212 ms / p95 219 ms — 3.8 detections per
second against a 59 fps render loop, which is the point of decoupling the two.

Three things in that table are worth more than the headline number:

- **CUDA is flat between 320px and 640px** (13.10 → 13.88 ms) while CPU nearly quadruples. A nano
  model does not saturate a 5070; the GPU is bound by kernel launch overhead, not arithmetic. That
  is also why CPU *beats* CUDA at 320px.
- **INT8 is 2.3× slower than FP32 under the CUDA provider.** The QDQ quantize/dequantize nodes are
  not fused into INT8 tensor-core kernels there, so you pay for the casts and get nothing back.
  INT8 earns its place on CPU and in WASM — memory-bound targets — not on bare CUDA. Shipping INT8
  because "quantization is faster" without measuring would have made the GPU path 2.3× worse.
- **Dynamic shapes cost TensorRT 40%** (5.29 ms → 3.15 ms static). The browser wants one file that
  serves 320/480/640; TensorRT wants shapes nailed down. Both numbers are published rather than
  picking whichever flatters the design.

TensorRT INT8 does not appear because it does not work here: it rejects the QDQ graph
(`failed to create engine from network`, and on the dynamic export
`Reshape_5_output_0_pre_q has no shape specified`). Listed as a failure with its error text on the
Benchmarks page rather than omitted.

## Three engineering notes

### 1. INT8 quantization silently zeroed every class score

Static PTQ succeeded, produced a model 3× smaller, ran without error, and detected nothing.

YOLO11's graph ends with a single `Concat` joining box coordinates in pixel units (range 0–640) to
sigmoid class scores (range 0–1). QDQ assigns one quantization scale per tensor, and a `Concat`
output is one tensor: calibrated over the union range, that scale is ≈2.5, so every class score —
all of which are below 1.0 — rounds to exactly zero. The box channels are large enough to survive,
so the model kept emitting perfectly plausible geometry with no objects attached.

```
fp32  boxes[min=2.57 max=637.18]  scoreMax=0.93992  ->  5 detections
int8  boxes[min=0.00 max=640.05]  scoreMax=0.00000  ->  0 detections
```

Fix: keep the head's elementwise tail (sigmoid, DFL softmax/projection, box arithmetic, output
concat) in float32; all 88 backbone and neck convolutions stay INT8. That is where the compute
actually is, so the speedup survives the fix. See `select_head_tail_nodes` in
[`ml/quantize_int8.py`](ml/quantize_int8.py).

### 2. NMS is deliberately not in the graph

Exporting with `nms=True` puts a `NonMaxSuppression` node in the model. The WebGPU execution
provider cannot run it, so ONNX Runtime partitions the graph and syncs GPU→CPU on every frame.
Exporting pure tensor ops keeps the model GPU-resident; decode and NMS live in
[`web/lib/decode.ts`](web/lib/decode.ts) and [`web/lib/nms.ts`](web/lib/nms.ts), mirrored by a numpy
reference in [`web/api/_pipeline.py`](web/api/_pipeline.py) that the serverless function shares.

NMS is class-wise, not global — suppressing across classes lets a car's box delete the person
standing in front of it, which quietly costs recall in exactly the crowded scenes that matter.

### 3. Two failure modes that produce no error at all

Both cost real debugging time and neither raises anything:

- **`HTMLImageElement.decode()` never settles in a backgrounded Chrome tab.** The promise simply
  never resolves. Any visitor opening the link in a tab that is not in front would have seen a dead
  demo. Image sources now go through `fetch` → `blob` → `createImageBitmap`.
- **Multi-threaded WASM start-up can hang even when the page is cross-origin isolated.** Isolation
  is necessary but not sufficient — ORT still has to spawn its own thread-pool workers. Session
  creation hangs with nothing to catch. The app races start-up against a deadline and respawns the
  worker single-threaded; the retry must be a *new* worker, because ORT initialises its WASM runtime
  once per worker and reusing the stalled one hangs identically.

The demo surfaces its real thread count and execution provider in the badge row rather than
reporting what it asked for.

## Architecture

```
camera / video / image
  |  createImageBitmap        (only when the model is idle — see below)
  v
Web Worker
  |  letterbox to NxN, pad 114, RGBA -> CHW float32 /255
  |  session.run()            WebGPU, or WASM with N threads
  |  decode [1, 84, anchors]  -> candidates
  |  class-wise NMS
  v
main thread: redraw last known boxes every animation frame
```

The render loop and the detection loop are independent. The canvas redraws at display rate while
frames reach the model only when it is idle — checked *before* the frame is captured, so a 220 Hz
render loop feeding a 10 Hz model does not allocate and discard 210 bitmaps a second competing with
the inference it is supposed to feed.

One model file serves 320/480/640 via dynamic spatial dimensions, so the resolution control is a
genuine latency/accuracy trade-off rather than three downloads.

## Reproducing

```bash
cd ml
python -m venv .venv
.venv/Scripts/python.exe -m pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

```bash
python export_onnx.py   --config configs/coco.yaml   # -> web/public/models/*-fp32.onnx
python quantize_int8.py --config configs/coco.yaml   # -> *-int8.onnx, static PTQ
python eval_map.py      --config configs/coco.yaml   # -> results/accuracy.json
python bench.py                                      # -> results/bench.json
```

```bash
cd web && npm install && npm run dev
```

Then open `/selftest` — it runs the full pipeline on the main thread and through the worker and
asserts they agree, which is the fastest way to tell a real regression from an environment quirk.

## Deploying

Vercel project with **Root Directory = `web`**. The build syncs the ONNX Runtime WASM artifacts into
`public/ort/` (`npm run sync:ort`) so nothing is fetched from a CDN at run time, and
`next.config.mjs` sets the COOP/COEP headers that multi-threaded WASM requires.

**WebGPU is implemented but is not the default.** On the development machine the WebGPU provider
creates a session, warms up on zero tensors in ~1 s, reports ready — and then never returns from the
first inference on a real frame, with no error and no rejection. Every inference is therefore bounded
by a deadline inside the worker, which reports a timeout so the app can rebuild on a backend that
works. `Auto` resolves to WASM, verified end to end; WebGPU stays selectable and is labelled
experimental.

**A `WASM ×1` badge is usually not a fallback.** Thread count is `min(4, reported cores − 1)`, and
`navigator.hardwareConcurrency` is whatever the browser chooses to report — Chrome reports 2 on a
24-thread CPU in some contexts, which makes 1 the correct answer. The badge shows the threads the
worker actually got, and the worker's own cross-origin isolation, rather than what was requested.

## Known limits and what I'd do next

- **The COCO row is a control, not a custom model.** Custom fine-tunes for PPE/safety, traffic and
  retail-shelf detection are the next milestone; the pipeline is already parameterised by dataset
  config, which is the point of building it this way.
- **mAP is evaluated on a small subset**, not full COCO val2017. Stated precisely on the Benchmarks
  page rather than rounded up into something it isn't.
- **No Jetson numbers.** TensorRT figures here are from a desktop RTX 5070; claiming embedded
  latency without embedded hardware would be dishonest. A Jetson Orin Nano is the obvious addition.
- **The WebGPU path is not always faster than threaded WASM** for a model this small — kernel launch
  overhead is a real fraction of a 3.6 MB model's runtime. The benchmark page reports both rather
  than assuming the GPU wins.
